1. Mission
Create a complete original action-puzzle game for the Sega Genesis / Mega Drive in which the player has twelve seconds per attempt to act inside a deterministic room or encounter.
When the timer expires—or the current incarnation is destroyed—the encounter resets. The player’s previous input sequence becomes an autonomous echo that replays those exact actions in the next attempt. Each new attempt adds another concurrent echo. The player succeeds by composing multiple past attempts into a synchronized solution.
The game must feel immediate and arcade-like rather than like a slow programming exercise. It should combine:
Top-down action.
Tactical puzzle solving.
Shooting.
Environmental interaction.
Light stealth.
Deterministic choreography.
Time-loop planning.
Boss encounters based on concurrency rather than merely large health pools.
The game’s mechanics, fiction, audiovisual progression, and implementation should all express the same idea:
> Useful work survives the reset, and repeated attempts compound into intelligence.

The player should be able to understand the central idea by watching one successful encounter:
A single incarnation enters a room and fails after twelve seconds.
The room resets.
The previous incarnation repeats its actions while the current player moves differently.
The room resets again.
Three or more incarnations perform synchronized roles.
The growing plan becomes visible and audible.
The final incarnation crosses the threshold because the earlier incarnations preserved useful work.
The screen confirms:
PROGRAM STABLE

14. Main runtime architecture
14.1 Frame model
Use a deterministic fixed-frame simulation.
Primary NTSC model:
One authoritative game step per displayed frame unless a documented scheduler uses a defensible subdivision.
The default loop lasts exactly 720 authoritative frames at 60 Hz.
Pause, menus, loading, and debug states must not accidentally consume loop frames.
Do not base authoritative behavior on wall-clock time.
14.2 Main loop
Establish a clear frame sequence such as:
Wait for frame synchronization.
Latch controller input.
Advance deterministic simulation.
Advance echoes.
Resolve interactions.
Update objects.
Build render state.
Prepare DMA and VDP command queues.
Submit time-critical video work during the correct interval.
Send bounded audio commands.
Update debug instrumentation.
The exact order may differ, but it must be explicit and deterministic.
14.3 Interrupt policy
Define:
Which work occurs in VBlank.
Which work occurs in HBlank, if any.
Which registers interrupt handlers preserve.
How long handlers may run.
Which shared structures are safe to touch.
How missed budgets are detected in debug builds.
Do not perform unbounded gameplay logic inside interrupts.
14.4 Fixed-point arithmetic
Use documented fixed-point formats for:
Position.
Velocity.
Acceleration.
Timers when subframe precision is required.
Provide tested host-side reference implementations where useful.
Avoid floating-point assumptions in the runtime.
14.5 Object system
Use bounded object pools.
Object classes may include:
Player.
Echo.
Enemy.
Projectile.
Interactive device.
Carryable object.
Hazard.
Effect.
Boss component.
Every pool must define:
Capacity.
Allocation behavior.
Overflow behavior.
Update cost.
Render cost.
Reset behavior.
Never use dynamic allocation on the cartridge runtime.

15. Echo system
The echo system is the signature mechanic and must be implemented as a first-class deterministic subsystem.
15.1 Input recording
For each active attempt, record at least:
Directional state.
A button state.
B button state.
C button state.
Relevant edge transitions or a compact representation capable of reconstructing exact frame input.
The canonical recording unit is the authoritative game frame.
Do not store a prerecorded video or per-frame full world state as the ordinary echo representation.
15.2 Playback
On subsequent attempts:
Each echo begins at the canonical spawn state unless a specific mechanic changes it.
Each echo replays its recorded input frame by frame.
Echo actions interact with the current world.
Echoes are subject to current collisions, hazards, enemy fire, movable objects, doors, and altered environment state.
Echoes may fail differently when the world has changed.
An echo is a replaying intention, not a holographic animation immune to causality.
15.3 Determinism
Given the same:
Level definition.
Initial persistent state.
Ordered echo recordings.
Current attempt recording.
Region timing mode.
Runtime version.
The engine must produce the same designated state hashes and encounter outcome.
15.4 Echo identity
Echoes must be visually distinguishable through a combination of:
Palette treatment.
Outline or highlight.
Number or symbol.
Animation cadence.
HUD identity.
Do not rely only on subtle color differences.
15.5 Collision policy
Define explicitly whether echoes collide with:
The current incarnation.
Other echoes.
Projectiles.
Carryable objects.
Enemies.
Doors.
Hazards.
Prefer a policy that preserves legibility and avoids accidental crowd-blocking while retaining meaningful world interaction.
15.6 Echo limits
Progressively unlock echo capacity.
A defensible campaign progression is:
Sector 1: one to two echoes.
Sector 2: up to three echoes.
Sector 3: up to four echoes.
Sector 4: up to five echoes and anchor mechanics.
Sector 5: up to six echoes in carefully budgeted scenes.
The exact numbers may change based on sprite, CPU, RAM, and design evidence.
15.7 Input storage
Design and document input storage.
A baseline uncompressed twelve-second recording is small enough to consider, but the system must still:
Bound memory.
Avoid overruns.
Support partial recordings after early death.
Support blank frames efficiently.
Support host-side replay import and export in debug tooling.
Produce a stable replay file format for automated tests.
Use compression only when it produces measurable value without risking correctness.
15.8 Echo management
When the player reaches the active echo limit, provide a deliberate mechanic such as:
Replace the oldest echo.
Select an echo slot to overwrite.
Preserve one protected echo.
Optimize a solution by reducing echo count.
Do not silently discard an echo without clear player feedback.

17. Anchor system
Anchors are introduced after the player understands ordinary echo composition.
An anchor allows a narrowly defined state transition to persist across resets.
Permitted anchor examples:
A hacked security node.
A moved energy core placed in an anchor socket.
A destroyed lock.
A changed conveyor direction.
A preserved bridge state.
A retained echo slot.
Anchor rules:
Only designated states may be anchored.
The player must understand what is anchored.
The number of anchors is tightly limited.
Anchor state must serialize deterministically.
Reset and replay must remain verifiable.
Anchors must create new planning possibilities rather than bypass level design.
Initial anchor capacity should be one. A later upgrade may permit two in selected encounters when hardware and design budgets permit.

49. Anti-cheating rules
The following do not satisfy the goal:
Producing only source code without a working ROM.
Producing only a ROM without reproducible source and tools.
Using a video, GIF, or scripted emulator overlay as gameplay.
Using runtime C as the true engine.
Using a prebuilt commercial or proprietary engine.
Copying a commercial game disassembly.
Copying proprietary art, music, levels, or code.
Using emulator memory patches to make tests pass.
Skipping the real reset and replay simulation.
Storing full prerecorded world-state videos as echoes.
Hard-coding the canonical replay outcome without simulating it.
Faking audio layers with an external audio player.
Silently lowering the echo count.
Silently reducing the campaign.
Marking tests skipped to obtain a green result.
Removing assertions because they are difficult.
Ignoring assembly warnings that indicate correctness risk.
Ignoring sprite dropout.
Ignoring PAL or region crashes.
Claiming hardware compatibility without ordinary emulator evidence and a documented hardware-oriented design.
Claiming visual review occurred when no image was inspected.
Claiming audio review occurred when no audio evidence was captured or heard.
Claiming performance without measurements.
Treating a title screen as a game.

52. Stalled-work policy

Three coherent attempts fail to improve the same measured gate.
The implementation oscillates between prior approaches.
The ROM fails without reproducible evidence.
An emulator result cannot be distinguished from a tool failure.
A budget result is too noisy to support a decision.
A hardware fact remains uncertain and materially affects correctness.
A required tool is unavailable and no defensible substitute exists.
When stalled:
Stop random edits.
Reduce to the smallest failing ROM or replay.
Capture listing, symbols, registers, memory, and emulator evidence.
Delegate an independent diagnosis.
Re-read the hardware contract.
Produce at least two materially different hypotheses.
Run the cheapest discriminating experiment.
Choose based on evidence.
Record the result.
If no defensible path remains, use the blocked terminal state rather than pretending completion.
